## Part 1 — Small kana (`っ`) in-cell parity

### Audit method

Per the task's own instruction: audit first, do not solve-first.

1. **Legacy classification search** (`src/components/PageCard.tsx`, direct
   Grep for `小さ|捨て仮名|拗音|促音|small.?kana|smallKana|ぁぃぅぇぉ|っゃゅょ`):
   only two matches, both unrelated (page-number minimum-size comment at
   line 1327, trim-guide-marking comment at line 1407). Small kana is also
   confirmed absent from all three of legacy's own yakumono regexes
   (`YAKUMONO_VPAL_TEST`/`YAKUMONO_HANG_START_TEST`/`YAKUMONO_HANG_END_TEST`,
   already fully quoted in round 13's own evidence doc). **Legacy has no
   small-kana-specific mechanism of any kind** — small kana paints exactly
   like any ordinary character (`justify-content: center`, `vpal` off).
   This rules out classification **C** (nothing to port).

2. **Direct regression proof against commit 639c63f**
   (`renderer/publication/smallKanaCellDebug.test.ts`): `っ` classifies as
   `NORMAL` under `classifyYakumonoAlignment` (not a HANG_START/HANG_END
   member), and two dedicated tests prove — by direct comparison of the
   actual paint-plan output, not by inference — that っ's own painted
   `yMm` AND its own real outline path commands (`glyphOutline`, round 7's
   mechanism) are byte-identical whether or not round 13's
   `yakumonoContext` is supplied. **Commit 639c63f changed nothing about
   っ's own paint position.** This rules out classification **A**
   (regression).

3. **Real ink-bbox measurement** (same test file): using
   `FontMetricsReader.glyphInkBBox` against the SAME glyph ID production
   paint actually resolves for each character (outline-first, per round
   7's own `resolveOutlineGlyphId`, cmap fallback otherwise), っ's real
   GSUB vertical-alternate glyph has a measurably smaller
   `(yMax - yMin) / unitsPerEm` ink-height fraction than either だ or た's
   ordinary glyphs — at the exact same uniform baseline anchor
   (`FALLBACK_BASELINE_RATIO`, round 5's real vmtx-derived 0.88, uniform
   across every glyph in this font). A smaller ink box anchored at the
   same fractional position within an unchanged, uniform cell necessarily
   leaves more visible white space around it — an inherent, expected
   property of "small kana drawn smaller within a full-em cell," not a
   positioning defect.

### Classification: **B — NO REGRESSION (pre-existing optical characteristic)**

No paint correction was made. There is no legacy mechanism to port (C is
false), and round 13 provably did not move っ's own paint position (A is
false). The reported "extra space" is real, measured, and expected —
`っ`'s own glyph occupies less of its em-square than an ordinary kanji, by
font design, matching legacy's own product (which does nothing special for
it either).

## Part 2 — Conditional cl-06/cl-07 → cl-02 pair suppression

### Why this is not round 8/11 again

Round 8 (`applyYakumonoCompression`) and round 11 (`yakumonoHalfBodyScope`)
were both **global** canonical models, applied via a scope table to every
adjacency it declared, and both were judged visually wrong **before**
round 13's real, font-grounded paint-time edge alignment existed. This
round's own instruction was explicit: test the SAME general idea — a
punctuation atom's own advance shrinking before a closing bracket — but
narrowed to exactly one pair (cl-06/cl-07 → cl-02) and combined with round
13's paint layer, which changes WHERE each glyph's own ink sits inside its
cell. Neither prior experiment was ever tested in that combination.

### Implementation

`core/compose/line.ts`'s `computeAtoms` gained one new function,
`conditionalYakumonoPairAdvanceTick(currentClass, nextClass, perCellAdvance)`:
returns `perCellAdvance - Math.round(perCellAdvance * 0.5)` when the
current atom classifies `cl-06` or `cl-07` (via
`RuleSetVersion.characterClassFor` — the SAME generic, data-driven lookup
every other class-aware Core module already uses, never a hardcoded
character) AND the immediately-following atom classifies `cl-02`;
otherwise returns `perCellAdvance` unchanged. `computeAtoms` now takes
`ruleSet` again (removed in round 13, since nothing needed it) and, for
TEXT atoms only, looks ahead to the next real atom's own owning unit —
skipping any zero-width marker boundary — to classify both sides. RUBY/
SEMANTIC_RUN/TCY/IMAGE atoms are never eligible on either side (none of
those unit kinds carry a classifiable literal character via
`literalTextForAtom`).

This is a real, narrow, evidence-scoped **canonical advance** change —
not a paint-only correction, and not global. `RuleSetVersion` itself
carries no new scope-table field (unlike rounds 8/11); the rule reads
character-class data through the same existing lookup every other
kinsoku/overhang computation in this file already relies on.

### Controls verified

- `た。次` / `た、次`: 。/、 followed by ordinary text keeps its full,
  uniform 1-cell advance — unaffected, unchanged from round 13.
- `」次`: a closing bracket followed by ordinary text is unaffected (rule
  only fires on the punctuation SIDE, cl-02 is never the trigger).
- `先「次`: an opening bracket (cl-01) is never a trigger, before or
  after.
- `。。`: two consecutive cl-06 atoms — rule never fires (next class is
  cl-06, not cl-02).
- Glyph size (`fontSizePt`) is unaffected for every character in `た。」`/
  `た、」`, including the compressed ones — proven directly at the
  Publication paint layer (`targetedYakumonoQa.test.ts`).
- No source/SourceSpan mutation; deterministic (same input composes
  byte-identical output twice).
- っ (small kana) is completely unaffected — not a cl-06/cl-07/cl-02
  member.

### Known, disclosed side effect

Because this is a real canonical-advance change (unlike Part 1), line/page
capacity for the SPECIFIC adjacency cl-06/cl-07 → cl-02 is very slightly
increased (a half-cell more content can fit at that exact boundary) — an
expected, inherent consequence of "pair spacing/advance contribution," as
the task's own framing anticipated. No other adjacency's capacity is
affected.

### Round 13 tests updated (not deleted)

Two tests in `yakumonoLegacyParityQa.test.ts` and one in
`glyphSizeIndependence.test.ts` asserted UNIFORM advance for `た。」` /the
`。→」` pair inside the reported sentence — true under round 13's own

preserved and re-verified, only the one now-intentionally-different pair
is updated.
