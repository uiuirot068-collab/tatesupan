## 1. Roadmap contract (§B3) and how it is met

| Roadmap requirement | B3 |
| --- | --- |
| Add the two questions to the **existing** user report/review area | A third tab **見直し** in the existing β 報告 modal (`BetaFeedbackModal`). The 報告 button is the only entry; nothing was added to the top toolbar, the Review Hub panel or the footer. |
| Q1 `見直しのフッター表示は最大2枠で足りていますか？` — `足りている` / `もう1枠ほしい` / `もっとほしい` / `常時表示は不要` | Exactly that wording and order. The "2" is read from the real footer maximum (`REVIEW_HUB_FOOTER_MAX`), so the question cannot drift from the product. Nothing is preselected; no answer is marked as recommended. |
| Q2 `「見直し」の中で、よく使っているものを選んでください`, maximum 2 selections | Checkboxes, refusal of a third selection (`toggleReviewHubFavorite`). |
| Q2 initial choices: 文章チェックβ / 描写語・修飾表現チェックβ / 音読β / 文字数カウント | Choices are **generated from the Review Hub registry** (`REVIEW_HUB_TOOLS`), so today they are `文章チェックβ` and `文字数カウント` only. 描写語・修飾表現チェックβ and 音読β are not implemented/released yet (B4/B5), and the roadmap guardrail forbids asking about unreleased features. When B4/B5 register their tool in the Hub, the choice appears automatically — no B3 change needed. |
| Do not ask before the feature is accessible / do not ask non-users about features they lack | The tab exists only in a build that contains the Hub; it is opened by the writer on purpose; its first line says to answer only if they have used 「見直し」; every question is optional and free text alone is enough to send. Choices never include an unreleased tool. |
| Do not steer to "2 is right" | Neutral question; four symmetric choices; no default. |
| Do not turn answers into feature keep/remove decisions | Answers are recorded together with the session counters and the current pins so a human can read them next to usage and UI-density evidence. |
| Release is not "fully complete" until answer collection is verified | Verified with a real browser against a stub of the transport (see §5). A live-destination check is a Human QA item (`B3_HUMAN_QA.md`). |

## 2. Existing feedback transport found (reused unchanged)

```
報告 button (EditorPane, only when NEXT_PUBLIC_BETA_FEEDBACK_ENABLED=true)
  → BetaFeedbackModal (Turnstile + honeypot + visible 使用環境 summary)
  → submitBetaFeedback()  src/lib/betaFeedbackClient.ts
  → Supabase Edge Function `beta-feedback`  (supabase/functions/beta-feedback/index.ts, verify_jwt=false)
       ├─ Google Apps Script → Spreadsheet, sheet 「気になる事」  ← canonical record
       └─ Discord webhook → FEEDBACK forum channel, one thread per report (`気になる事｜<id8>｜<first chars>`)
```

Owner / recipient: the TateSpun developer (project owner) — the Supabase project, the Apps Script Web App + Spreadsheet and the Discord forum are all on the owner's side (`docs/supabase/beta-feedback-setup.md`, "Human 側で deploy 済み").

* **No new endpoint, table, function, migration, field, env var or auth flow.** The Edge Function is not modified (so nothing needs redeploying for B3).
* The survey is sent as an ordinary `feedback` submission. The Edge Function allow-lists `clientContext` fields and (for `review`) the 15 checklist labels, so structured *fields* would have needed a backend change; a plain-text `message` needs none. That is the single reason for the text encoding, and it keeps the design inside the "reuse the existing transport" rule.
* Retrieval: filter the 「気になる事」 sheet's message column (or the Discord forum) for lines starting with `【見直しアンケート】`.
* Existing automatic remote telemetry: **none found** (a search of `src`, `package.json` and `next.config.ts` for analytics / beacon / gtag / Sentry / PostHog / Mixpanel-style code hits only test files and docs, no runtime code). B3 adds none.

## 3. Exact data

### Sent (only when the writer presses 匿名で送信する on the 見直し tab)

`message` (text, ≤ ~1.3k chars; the transport limit is 4000):

```
【見直しアンケート】
Q1 見直しのフッター表示は最大2枠で足りていますか？: <選んだ答え | 未回答>
Q2 見直しでよく使うもの: <文章チェックβ、文字数カウント の部分集合 | 未回答>
フッターに表示中: <現在のフッター表示のツール名を表示順に「 → 」で連結 | なし>（n/2）
フッター表示を変えた回数: N回（このページを開いてから）
見直しを開いた回数: N回（このページを開いてから）
自由記述: <書き手が入力した文章 | （なし）>
```

plus what **every** existing report already carries (unchanged, already disclosed in the modal): the existing `clientContext` 使用環境 diagnostics (browser/OS/viewport/etc.), the Turnstile token, and the honeypot field. Pin count 0/1/2, pin ids/order and the two counters are all inside the lines above; the viewport class is already in the existing 使用環境.

The 見直し tab lists the "フッターに表示中 / フッター表示を変えた回数 / 見直しを開いた回数" values **before** sending ("回答と一緒に送られる情報"), generated by the same function that builds the message, so what is shown is what is sent.

### NOT sent

manuscript text · selected text · title · body · character names · file names · generated PDF/JPG · manuscript/document IDs · account/auth identifiers · new personal data · images (this tab has no file input). `buildReviewHubSurveyMessage` has no parameter that can carry any of these, ignores unknown fields (unit-tested with smuggled `content/title/fileName/documentId/selectedText`), and the E2E types unique sentinels into the manuscript body and title and asserts they appear nowhere in the outgoing request.

### Free text
Optional, clearly the writer's own input (max 1000 chars). Warning shown under the box: 原稿の文章・作品名・ファイル名は書かないでください。

## 4. Local-only state

* **In-memory counters** (`src/lib/reviewHubUsage.ts`): Hub opens and footer-pin changes since the page was loaded. Module memory only — **no localStorage/sessionStorage/IndexedDB key is created**, so B1's "opening/closing the Hub writes nothing" contract stays true (E2E proves it). They reset on reload and are never sent automatically; they leave the device only inside an explicit 見直し submission.
* B2's own pin selection (`tatespun.reviewHub.footerTools.v1`, browser-local) is only **read** by the modal (through the existing hook) to report the current pins. It is not modified by B3.
* B3 adds no other state. The modal is never opened by the app (`isBetaFeedbackOpen` starts `false`; the 報告 handler is the only place that sets it).

## 8. Rollback path

* Before release: do not merge/push the B3 commit. Base = `a46279abfc4dbda427a4d3466eb33b42bff95c0c`.
* After a future release: a normal forward revert of the B3 commit removes the tab, the model, the counters and the two one-line hook calls. Nothing has to be rolled back on the backend (nothing was changed there). Reports already received stay in the Sheet/Discord and remain readable as plain text.

## 9. Known limits (accepted for the beta)

* Answers are plain text in the 「気になる事」 sheet, not separate columns; analysis is a text filter on `【見直しアンケート】`. Structured columns would need an Edge Function + Apps Script change (a backend/privacy decision deliberately not made here).
* Counters are per page-load, not per device history; a writer who reloads between using the Hub and reporting shows 0. Persisting them would create a storage key and break B1's "writes nothing" contract, so it was not done.
* There is no link from inside the Review Hub to the 見直し tab (adding one would grow the Hub on 320–390px); the writer reaches it via 報告 → 見直し.
* Q2 offers only the two tools that exist today (see §1).
* On a 320×568 phone the modal's own scroll area is short (the existing Turnstile block and send row are pinned below it); the 見直し tab scrolls inside it like the other tabs. The real Turnstile widget (not present in the stubbed E2E) adds its usual height.
