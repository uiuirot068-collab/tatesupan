# P2-L01 — Candidate 2 (Dedicated Shaping) — Shaping Evidence

- Status: Phase 2 PoC evidence, not a Phase 3 spec
- Tool: `harfbuzzjs` 0.4.15 (WASM build of real HarfBuzz), direction `ttb`, font scaled to 1000 units/em
- Font: Shippori Mincho Regular, fetched from the `google/fonts` GitHub mirror (OFL) into an out-of-repo scratch path for this PoC only — not committed, not a production asset change
- Raw data: `../candidates/c2-dedicated-shaping/shape-output.json` (generated by `shape.js`)
- Reproduce: `cd candidates/c2-dedicated-shaping && npm install && TSP_FONT_PATH=<path to ShipporiMincho-Regular.ttf> node shape.js`

## 1. Font's actual declared OpenType features (measured, not assumed)

Enumerated via `opentype.js` reading the font's own GSUB/GPOS tables:

```
GPOS: abvm, mark, mkmk, palt, vpal
GSUB: aalt, ccmp, dlig, frac, fwid, hwid, jp78, jp83, liga, nlck, ordn, salt, ss01, ss02, sups, vert, vkna, vrt2
```

**This font does NOT declare `vhal`, `vkrn`, or `vchw` at all.** Requesting them via HarfBuzz's feature string is a silent no-op (HarfBuzz does not error on an unsupported feature tag — it simply has no lookup to apply). This directly satisfies the loop's "measure it, do not assume it works" requirement: three of the eight features listed as candidates in the loop brief are not present in the one font under test.

## 2. What `vert`/`vrt2` do here

Both are already applied automatically by HarfBuzz once `buffer.setDirection('ttb')` is set (confirmed: explicitly requesting `vert=1` or `vrt2=1` produces byte-identical output to the default/no-features run). Their effect: GSUB glyph substitution to the font's vertical glyph variants — e.g. U+305D そ → glyph `uni305D.vert`, U+3060 だ → `uni3060.vert`. Punctuation gets substituted to its **vertical presentation form** codepoint instead of a `.vert` glyph name — U+3002 。→ `uniFE12`, U+3001 、→ `uniFE11`. This is standard, expected, and matches Phase 1's P1-L04 finding (`vert`/`vrt2` work "for free" per the font's own tables).

## 3. What `vpal` actually does here — the load-bearing finding

`vpal` ("Proportional Alternate Vertical Metrics") is declared under **GPOS**, not GSUB, in this font. Measured effect on the two flagged sequences (`それまでだ。けれど` and `気づけば、どこへ`, both shaped with `buffer.setDirection('ttb')`):

| glyph (source char) | yAdvance, default | yAdvance, `vpal=1` | yOffset, default | yOffset, `vpal=1` |
|---|---|---|---|---|
| そ | -1000 | -1000 | 0 | 17 |
| れ | -1000 | -1000 | 0 | 43 |
| ま | -1000 | -1000 | 0 | 4 |
| で | -1000 | -1000 | 0 | -53 |
| だ | -1000 | -1000 | 0 | 24 |
| **。** | **-1000** | **-1000** | 0 | -11 |
| け | -1000 | -1000 | 0 | 29 |
| づ | -1000 | -1000 | 0 | 103 |
| ば | -1000 | -1000 | 0 | 2 |
| **、** | **-1000** | **-1000** | 0 | -6 |
| ど | -1000 | -1000 | 0 | 3 |
| こ | -1000 | -1000 | 0 | 125 |
| へ | -1000 | -1000 | 0 | 268 |

**`yAdvance` (the column-pitch each glyph consumes) is unchanged by `vpal` for every glyph tested, punctuation included — always exactly -1000 (a full em).** `vpal` only nudges each glyph's `yOffset` (its position *within* its own unchanged 1000-unit advance box), and it does so for ordinary kana too (づ→103, こ→125, へ→268), not only for punctuation. In other words: in this font, `vpal` is a general vertical kerning/positioning table, not a punctuation-advance-narrowing feature. `vhal`/`vkrn` (also tested) are no-ops here (§1) and change nothing. `vchw` is likewise absent.

**Consequence for the loop's central question:** HarfBuzz + this font's own declared OpenType features, used as-is, cannot close the visible-gap problem after 。/、 — because none of the font's own vertical GPOS features narrow their advance. Closing it would require either (a) a different/more complete font, or (b) an explicit, principled advance override for the 句読点 category, derived from measured glyph ink extents (see POC_MEASUREMENTS.md) — which is a **category rule**, allowed under Master §5.4, not a magic number, but it is a Phase 3 design decision, not something this PoC should bake in silently (Master §5.3).

## 4. Glyph identity spot-check (visual, not just numeric)

`render-svg.js` draws the actual HarfBuzz-shaped glyph outlines (via `font.glyphToPath`, real vector paths, no browser text shaping involved) into SVG and confirms visually (see `outputs/c2-default.svg`, `outputs/c2-vpal-vhal-vkrn.svg`, and the debug crop reproduced in the loop log) that:
- Glyph shapes are correct, right-reading, not mirrored or rotated wrong.
- The 。glyph (`uniFE12`) visibly occupies only the upper portion of its box; a large blank run follows it before the next glyph starts — **this reproduces the exact "だ。けれど" visible-gap symptom named in the loop brief, using real dedicated shaping, not FixedSlot/browser DOM.**

## 5. What was NOT tested (time-boxed out, recorded per loop rules)

- Font variants other than Shippori Mincho Regular (no font-fairness alternative was available/needed — see README).
- `vchw` (contextual half-width variants) — absent from this font, so untestable here; would need a different font to evaluate the feature itself.
- GPOS pair-kerning between specific adjacent category pairs beyond the two flagged sequences (e.g. opening-bracket-follows-punctuation) — out of scope for this loop's timebox.
