# Core Implementation Risk Register

- Status: **P3-L03: REVIEWED / FROZEN FOR IMPLEMENTATION (2026-09-06, Master v1.8 §28).** Core implementation: NOT STARTED. Created fresh at P3-L03 — no prior risk register existed for Phase 3 implementation specifically.

| Risk | Impact | Likelihood | Early detection | Mitigation | Rollback | Blocking milestone |
|---|---|---|---|---|---|---|
| **Unicode/source offset mismatch** (code-point vs. UTF-16 index confusion) | High — silently wrong SourceSpans corrupt every downstream feature (ruby, breaks, export) | Medium — the exact class of bug the Contract's §4 code-point decision was designed to prevent, but a boundary bug is still possible at the Normalizer/Core seam | P3-L05's F16 fixture + adversarial "naive `string[i]` would break this" test, run every Loop after L05 | Single, tested conversion boundary (`source/graphemeSafety.ts`) — no other module performs its own UTF-16↔code-point math | Revert the offending module to its last checkpoint; the conversion boundary itself is small and independently re-verifiable | Blocks P3-L05 exit; if found later, blocks whichever Loop introduced the regression |
| **Grapheme segmentation inconsistency** (emoji ZWJ/variation-selector/combining-mark edge cases) | Medium — visible only on emoji/rare combining sequences in body text, but could silently fracture a user-perceived character (INV-011) | Low-Medium — Master §23's emoji policy is already limited/disclosed, narrowing real-world exposure | F16 fixture, `Intl.Segmenter`-based assertion tests | Rely on `Intl.Segmenter` (platform-native, well-tested) rather than a hand-rolled grapheme algorithm | Revert `source/graphemeSafety.ts` to last checkpoint | Blocks P3-L05 exit |
| **Rule table incomplete** (a jlreq class/rule not yet encoded in `defaultRuleSet.ts`) | Medium — a real manuscript hits an unclassified character and either crashes or silently mis-breaks | Medium — the full 900-cell pairwise grid (P3-O01 residual) is still not text-extracted | F04/F05 fixtures cover the two HG-decided classes; a "every code point in a fixture maps to a known class" assertion test catches gaps early rather than at Production time | Treat any unclassified character as a `LayoutWarning` (not silent `ALLOWED`), never guess a class | Revert `rules/defaultRuleSet.ts` to last checkpoint; data-only change, no cascading code revert needed | Blocks P3-L06 exit for the two HG classes; the 900-cell residual gap is tracked (P3-O01) but does not block Core Contract entry per existing decision |
| **Floating-point leakage into GeometryTick logic** | High — silently breaks INV-013/INV-005 (determinism), compounds across many pages before being noticed | Medium — easy to accidentally write `x * 0.5` instead of integer tick math during composition/ruby-overhang calculations | A lint-level or test-level check: any `GeometryTick`-typed value must remain an integer after every arithmetic op used in the codebase; multi-page determinism test (F19) would eventually surface drift but that is a late, expensive detection point | Centralize all tick arithmetic in `geometry/` (rounding/division rules defined once); no module outside `geometry/` performs raw tick division | Revert the offending composition module to last checkpoint; `geometry/` itself is small and stable from P3-L04 | Blocks P3-L09/P3-L11 (line composition, ruby placement — the two densest arithmetic sites) |
| **Measurement Provider instability** (fake provider's fixture values drift or get edited inconsistently across Loops) | Medium — a changed fake-provider constant silently changes many fixtures' expected output at once, masking a real regression as a "fixture update" | Low-Medium — mitigated by P3-L08's documented fixture-value table | Any fake-provider constant change requires re-running the full fixture suite and reviewing every resulting diff (golden-output policy, `CORE_TEST_STRATEGY.md` §4) | Fake provider values are versioned/named constants, not inline magic numbers, cited by name in fixtures | Revert `measurement/fakeProvider.ts` to last checkpoint | Blocks any Loop from P3-L08 onward if constants are found unstable |
| **Ruby segment model too narrow** (jukugo `segments` shape can't represent a real future case, e.g. group-ruby) | Medium — a future ruby refinement requires a breaking schema change | Medium — group-ruby (P3-O15) and exact overhang budgets (P3-O06 residual) are both explicitly still OPEN | Any new ruby-related Human decision (P3-O14/O15/O06 residual) reviewed against the current `RubyUnit`/`RubySegment` shape before implementation, not after | `rubyKind` is an extensible discriminated union (`"ATOMIC" \| "JUKUGO"`, room for a future `"GROUP"` variant); `segments` is optional, not required | Schema addition is additive (new union member), not a breaking rewrite, if designed carefully at P3-O15 resolution time | Does not block P3-L11; blocks a future group-ruby-specific Loop until P3-O15 resolves |
| **Renderer reflow drift** (a future Preview/Publication renderer quietly re-measures and changes Core's decided layout) | High — directly violates INV-002/INV-009, the entire Core/Renderer separation the whole Phase 3 reset (Master §0) exists to fix | Low during Core-only Loops (no renderer exists yet to violate this); Medium once Stage D/E (migration plan) begins | Comparison adapter (Stage C) diffing old-vs-new logical output; a renderer-level test asserting it never calls back into Core's layout functions | Contract §28's renderer rule is restated as a structural constraint: no renderer code path may import anything from `core/` except the final `CanonicalDocument` read-only value | Not a Core-Loop rollback — this risk activates later; mitigation is architectural (no shared mutable state), not a revert | Blocks Stage D/E of the migration plan, not any P3-L0x Core Loop |
| **Legacy capacity assumptions leaking into v2** (an unexamined `pageLayout.ts` behavior — e.g. the P3-O12 B5/B6/新書 discrepancy — gets silently copied instead of re-derived from Contract §19) | Medium — a plausible-looking but wrong capacity formula passes Core's own tests (which don't know the "correct" Production answer) but diverges from real Production behavior | Medium — P3-O12 is already a known, named discrepancy | Stage C comparison adapter's page-count diff against real Production presets; P3-O12 stays explicitly OPEN in `PHASE3_OPEN_ITEMS.md`, not silently assumed resolved | `pageLayout.ts` is read-only reference evidence, never imported; capacity math is re-derived from Contract §19's formula family and tested against F18/F19, then reconciled with P3-O12 at Stage C, not before | Revert the specific capacity-formula change in `compose/column.ts`/`compose/page.ts` | Does not block P3-L09/L10; blocks Stage C exit until P3-O12 is reconciled |

| **Overlarge implementation Loop** (a Loop's scope creeps past its timebox and produces an opaque, hard-to-review, hard-to-roll-back change) | Medium — makes rollback and review both harder, defeats the point of Loop decomposition | Medium — P3-L09 and P3-L11 are the two largest-budgeted Loops (90 min) and the most likely to creep | Each Loop's own timebox + the roadmap's explicit "split into a new Loop ID rather than silently extend past 120 minutes" rule | Loop roadmap already pre-splits the two largest concepts (line composition, ruby) as far as is practical without going below useful vertical-slice size | Split into `P3-L0Na`/`P3-L0Nb` at the point of overrun, each independently checkpointed | Self-limiting by roadmap design; watched at every Loop's own checkpoint audit |

## Highest-priority mitigation

The floating-point leakage risk and the Unicode/source-offset risk are the two most likely to cause **silent** (not loudly-failing) correctness bugs that compound before detection — both get dedicated adversarial tests starting at their introducing Loop (P3-L04/P3-L05) rather than being caught only by later end-to-end fixtures (P3-L15).
