# Phase 1 — Architecture Research Matrix

- Status: Phase 1 draft, pending Human Review — **no architecture selected**
- Evidence base: `../../research/browser/css-svg-vertical-japanese-research.md`, `../../research/shaping/canvas-harfbuzz-shaping-research.md`, `../../research/pdf/publication-output-path-research.md`, `../../research/typography-standards/jlreq-jis-opentype-standards-research.md`

- Per Master §7, this document investigates and compares; it does not select. Selection happens at a later Human Gate after Phase 2 PoC evidence, per Master §14.

## Families investigated

| Letter | Family | One-line description |
|---|---|---|
| A | Browser DOM/CSS layout | `writing-mode: vertical-rl` + DOM, either relying on native layout or (as today) using DOM purely as an absolutely-positioned paint surface |
| B | Canvas-based rendering | 2D canvas as paint target, glyphs drawn individually |
| C | SVG-based rendering | SVG `<text>`/`<tspan>` with explicit per-glyph coordinates as paint target |
| D | Dedicated shaping + custom layout | HarfBuzz-via-WASM (or a JS OpenType parser) computes real glyph shaping/advance; a hand-built jlreq-grade layout engine sits on top |
| E | Direct publication renderer | PDF/JPG produced from the layout result directly, not by screenshotting a live Preview DOM |
| F | Hybrid | Canonical Layout Engine (Family D core) + independently-chosen Preview renderer + independently-chosen Publication renderer, per Master §1.2–1.3's explicit allowance for different Preview/Publication technology |

## Cross-cutting finding (from all four research passes independently)

Every rendering technology researched (DOM/CSS, Canvas, SVG) shares the same structural limitation: **none of them natively solve Japanese vertical kinsoku, hanging punctuation, long-ruby overflow, or TCY auto-detection** — each either leaves this to unshipped/UA-discretionary spec features (browser research), or has no concept of vertical text at all (Canvas research). A custom logical layout layer, grounded in jlreq/JIS X 4051 (typography-standards research), is required **regardless of which technology paints the result**. This directly confirms Master §7's premise that the current FixedSlot/one-span-per-character pattern exists for a real reason (not an accident to casually discard) — but also confirms Master's instruction not to preserve it as-is: the *positioning discipline* it embodies is sound and portable to any paint surface (DOM, Canvas, SVG, or PDF operators); its specific DOM/html-to-image implementation is not the only way to deliver that discipline.

This is why the matrix does not recommend eliminating custom per-character layout in favor of "just use native CSS/SVG/Canvas layout" for any family — no evidence supports that native layout alone would clear Publication Quality, for any of the three paint technologies.

## What this rules in / out at this stage

- **Not ruled out:** any of A/C/D/E/F as a *component* of a final architecture — each has a legitimate role (A for Preview's editing surface, D for the shaping/layout core, E's sub-paths for Publication).
- **Weakened, not ruled out:** B (Canvas) as the *editor's* interaction surface, given the documented cost of rebuilding caret/selection/IME from scratch with no compensating quality benefit over A/C for this specific axis. Canvas remains viable as a **Publication/JPG rasterization target** (paired with D's shaped output), just not as a strong candidate for the live editing surface.
- **No family is selected.** Per Master §7 and this Phase's own charter, this matrix narrows the field for Phase 2 PoC comparison — it is not a decision.
