### P4-7 の中身

- PDF はノンブル・柱を横書きの1行の文字として書く（`horizontalFurnitureCommand`）。大きさ＝ノンブル・柱の文字の大きさ、横は「左はし・中央・右はし」を文字の送り幅（字の幅の合計）で合わせ、縦は jsPDF の `baseline:"middle"`（置き場の中心＋0.35 字）に文字の基準線を置く。
- 前のプレビュー: 1行の高さの CSS の箱を置き場の中心にそろえ、ブラウザが箱の中に字を置いていた。箱の中心と字の中心は書体ごとにちがうので、ノンブル・柱が下に、隠しノンブルは上にずれた。
- 今のプレビュー: 同じ書体ファイルの横書きの字の形を、PDF と同じ基準線・同じ送り幅で描く（`furnitureRunPlacement`、`PageFurnitureText`、`V2HiddenNombreOverlay`）。字の形は本文と同じ置き場（`usePreviewGlyphOutlines`、1字形1回だけ）。奥付のページの柱・ノンブルも同じ部品。
- 書体ファイルを読み終わるまでと、書体にない字がある時と、Web 閲覧用の紙は、これまでどおりブラウザの文字。

### はかった結果（`npm run test:e2e:furniture-parity`、この環境）

プレビューの字の形の外形と、PDF（600dpi で画像にした）の字の外形の、上・下・左・右のはしの差。

| 場面 | 1ページ目 | 2ページ目 |
|---|---|---|
| 文庫・しっぽり明朝・9pt・柱は上・ノンブルは小口 | 0.01〜0.07mm | 0.00〜0.06mm |
| 文庫・Noto Sans・9pt・柱は下・ノンブルは中央 | 0.01〜0.08mm | 0.03〜0.08mm |
| A5・Zen オールド明朝・6pt | 0.00〜0.07mm | 0.03〜0.07mm |

- 残りの 0.08mm 以内は、PDF を画像にする時のふちのにじみ（600dpi で1画素 0.04mm）くらい。
- 前の描き方は、TSP-PRINT-002 の比べでノンブル・柱が 0.2〜0.4mm 下。今回、同じ場面の画面の写真を前後で比べると、文庫のノンブルが約 0.25mm 下、隠しノンブルが約 0.4mm 上だった（写真どうしの比べなので目安）。
- 本文ページ全体の比べ（`test:e2e:print-parity`、文庫・しっぽり明朝と長い奥付）は前と同じ（1ページ目 21.3%、0.25mm）。奥付のページ数はプレビュー・JPG・PDF で同じ。

### 奥付の中身

- 前（TSP-PRINT-001）: 同じ高さに描く文字（標準・罫線の型の「項目名」と「中身の1行目」）だけをいっしょに動かしていた。中央の型は項目名が中身の上の行にあるので、項目名がページの最後、中身が次のページの頭になることがあった。中身が折り返して2行以上になる時は、どの型でも中身の途中でページが分かれた。
- 今: 奥付の文字に「何番目の項目か」（`ColophonRenderText.row`）を持たせ、同じ項目の行をまとめて送る（`paginateColophonRenderPlan`）。1ページに入りきらないほど長い項目は、まとめて送っても分かれるので送らず、その場から行ごとに次のページへ続ける（前のページに空きを残さない）。自由欄は1行ずつ。
- 1行がページより高い時（余白をとても大きく、文字をとても大きくした時）も、空のページは作らない。中央の型で、行は全部入るのに最後の項目の下の間だけが入らない時は、その間を切って1ページにする。
- プレビュー・JPG・PDF は同じページ割りを使う（前から）。

### 3D の本の絵の中身

- プレビューの字の形は、1字形を1回だけ隠した置き場（`<defs>`）に置き、各ページは `<use href="#…">` で指している。画面を写す道具（html-to-image）は、指している先を写す絵に入れるのを `xlink:href` の時しかしないので、全部の字が「指す先なし」になり、3D の本のページは白紙だった。
- 写す間だけ `href` を `xlink:href` にも写す（`exposeGlyphUsesForCapture`、写し終わったら戻す）。3D の本のページに本文・柱・ノンブル・隠しノンブルが出るのを、この環境の画面で確かめた。
- 同じ道（`capturePageToCanvas`）を通る、緊急の戻し（LEGACY）の JPG/PDF も同じ。ふつうの JPG/PDF は描き方の表から描くので、もともと関係ない。

### JPG の基準線の中身

- 描き方の表の「middle」の文字は、PDF（jsPDF）では置き場＋0.35 字に基準線。JPG（Canvas）の「middle」は字の箱の中央で、基準線は＋0.38 字（Chrome、同梱の書体すべて）、Node の書き出しはもっと下だった。
- JPG も PDF と同じく、基準線を置き場＋0.35 字に置く（`rasterTextBaseline`、ブラウザと Node の両方）。ノンブル・柱・縦中横・奥付の文字に効く。

## デバッガー10人の点検（10/19）

10人とも同じ範囲・同じ項目で点検した。報告とくらべは `/mnt/project-files/TateSpun/tsp-print-003/qa10/`（r1〜r10.md、COMPARE.md）。見つかったものと直し方:

1. 奥付で1行がページより高いと空のページができた（7人）→ 空のページを作らない（上）。
2. JPG で、横に回して描く「ー」（書体に縦書き用の形がない時だけの道）がずれた（10人）→ 回す文字は前の決め方（Canvas の基準線、ずらしなし）に戻した。
3. 3D の本などで同じページを同時に2回写すと、先に終わった方が後の方の字を消すおそれ（7人）→ 写している数を数え、最後の1つが終わるまで残す。
4. 写す処理が重くなるおそれ（7人）→ 3D の本は前は白紙だったので、字を写す分の時間は必要。LEGACY では字の形を使わないので増えない（5）。
5. LEGACY の画面でも柱・ノンブルが字の形になり書体ファイルを読んでいた（7人）→ V2 のページだけ字の形にする。
6. 計測の道具が実際に描かれた字を見ていなかった・場面が足りない（8人）→ ノンブル・柱・隠しノンブルを別々に比べ、画面に字があること・PDF にだけある字がないこと・ブラウザの文字に戻っていないことも確かめる。奥付のページ、ノンブルだけ別の書体、Web閲覧用の場面を足した。古い出力は消してから。
7. 点検用スクリプト2本がノンブルを div と思っていた（4人）→ 字の形の時も読めるようにした。
8. 古くなったコメント → 直した。
9. 柱に 𠮷 など特別な字があると PDF だけ位置がずれる（4人、前から）→ 直していない。理由は下。
10. 書体の読み込みと画面の描き直しがすれ違うと、しばらくブラウザの文字のまま（3人、前から）→ すれ違っても描き直すようにした。
11. 長い項目を新しいページから始めるので空きが残る（2人）→ 送らないようにした（上）。
12. 中央の型で、最後の間だけが入らない時に少しはみ出す（1人、前から）→ 直した（上）。

## 気づいたが直していないこと（理由）

- 飾り・挿絵・下の欄を V2 の描き方へ、と旧描画（LEGACY）を消すかは、引き継ぎで「余力があれば」「なつおが決める」なので、このループではしていない。
- 柱に 𠮷 などの字（Unicode の BMP の外の字）があると、PDF を作る道具（jsPDF）がその字を2字と数えて幅をまちがえ、PDF の柱だけ横にずれる（プレビューは正しい）。前からあり、直すには PDF の柱・ノンブルも本文と同じく字の形で描く必要がある（PDF の作り方を変える大きな変更）。P4-8 で飾りなどを PDF と同じ描き方にそろえる時にいっしょに考える。
- 柱は、エディターでは必ず小口側（Core の決まり）なので、「柱を中央」の場面は計測していない。
